# `datetime.fromisoformat()` — experiment diary

Branch: `exp-datetime/fromisoformat-fastpath`, off `main` at
`cecf564073f`.

## Goal

Evaluate whether the `fromisoformat()` family can be sped up on the
common ASCII / standard-layout cases without regressing:

- week-date and ordinal-date support
- timezone and midnight rollover behavior
- surrogate separator support in `datetime.fromisoformat()`
- subclass construction behavior

## Process

1. Inventory stdlib tests and third-party direct users of
   `date/time/datetime.fromisoformat`.
2. Define a small set of candidate parser-entry refactors.
3. Benchmark each variant against direct loops and representative
   third-party wrappers.
4. Validate semantics against the datetime test suite.
5. Feed the recommendation back into `Misc/cpython-perf-ideas.md`.

## Candidate refactors

- **Baseline** — current parser entry points.
- **ASCII direct path** — for ASCII input, avoid the sanitize/UTF-8
  conversion path and read directly from the compact unicode buffer.
- **Datetime calendar-prefix dispatch** — in
  `datetime.datetime.fromisoformat()`, skip the generic separator finder
  when the input starts with the common `YYYY-MM-DD` or `YYYYMMDD`
  calendar-date layouts.
- **Family-wide entry fast path** — extend the ASCII direct path across
  `date`, `time`, and `datetime`.

### Variant A — ASCII direct path in `datetime.datetime.fromisoformat()`

Change:

- For ASCII input, skip `_sanitize_isoformat_str()` and
  `PyUnicode_AsUTF8AndSize()`, and read directly from the compact
  Unicode buffer.

Exploratory result versus baseline (`ascii-direct-datetime.json`):

- `M1` `0.037121s -> 0.035492s` (`-4.39%`)
- `M2` `0.031049s -> 0.030190s` (`-2.77%`)
- `M3` `0.024950s -> 0.024691s` (`-1.04%`)
- `M6` `0.019107s -> 0.018402s` (`-3.69%`)
- `R1` `0.021452s -> 0.020656s` (`-3.71%`)
- `R2` `0.024321s -> 0.023243s` (`-4.43%`)
- `R5` `0.023107s -> 0.022070s` (`-4.49%`)
- `R7` `0.061712s -> 0.059678s` (`-3.30%`)

Conclusion:

- Worth keeping. The win is modest but real, and the patch is tiny.

### Variant B — add conservative ASCII separator dispatch

Change:

- On top of Variant A, add `_find_ascii_datetime_separator_fastpath()`
  for obvious `YYYY-MM-DD` and `YYYYMMDD` prefixes; fall back to the
  existing generic separator finder for everything else.

Exploratory result versus Variant A
(`ascii-direct-plus-separator.json`):

- `M1` `0.035492s -> 0.034974s` (`-1.46%`)
- `M2` `0.030190s -> 0.029905s` (`-0.95%`)
- `M3` `0.024691s -> 0.024473s` (`-0.88%`)
- `R2` `0.023243s -> 0.022004s` (`-5.33%`)
- `R5` `0.022070s -> 0.020680s` (`-6.30%`)

Some other workloads moved in ways this patch should not materially
affect, so I treated that exploratory run as noisy and confirmed the
final branch state with a clean sequential rerun against rebuilt `main`.

Sequential confirm versus rebuilt `main`
(`baseline-confirm-4-seq.json` vs `candidate-confirm-5-seq.json`):

- `M1` `0.038519s -> 0.035109s` (`-8.85%`)
- `M2` `0.032318s -> 0.029763s` (`-7.91%`)
- `M3` `0.025891s -> 0.024657s` (`-4.77%`)
- `M6` `0.019464s -> 0.018799s` (`-3.42%`)
- `R5` `0.023481s -> 0.022343s` (`-4.84%`)
- `R6` `0.102484s -> 0.100358s` (`-2.07%`)
- `R7` `0.062158s -> 0.060646s` (`-2.43%`)
- `M4` `0.051613s -> 0.051404s` (`-0.40%`)
- `M5` `0.050630s -> 0.051208s` (`+1.14%`)
- `R1` `0.020447s -> 0.020977s` (`+2.60%`)
- `R2` `0.023325s -> 0.023482s` (`+0.67%`)

Conclusion:

- This is the best patch from the experiment.
- The direct `datetime.fromisoformat()` common cases do get
  meaningfully faster.
- Ecosystem-wrapper impact is smaller and mixed, but still acceptable
  for a small single-file optimization.

### Variant C — extend the ASCII direct path to `date` / `time`

Change:

- Broaden the entry fast path across the whole `fromisoformat()` family.

Exploratory result (`family-wide-fastpath.json`):

- `M4` improved by about `-2.49%`
- `M5` improved by about `-4.39%`
- But the broader patch did not cleanly beat Variant B on the
  representative wrapper workloads, while increasing the amount of code
  touched.

Conclusion:

- Dropped. The extra surface area was not justified by a clear enough
  win.

## Validation

Build and test:

- `./configure --quiet`
- `make -j4`
- `./python -m test -j4 test_datetime`

Notes:

- Existing `test_datetime` coverage already exercises the important
  behavioral edges for this patch: week dates, timezone parsing,
  surrogate separator handling, midnight rollover, invalid strings, and
  subclass construction.
- I did not add new tests because the final patch intentionally stays
  inside existing parser-entry semantics and passed the full datetime
  suite as-is.
- A few parallel reruns during the investigation were visibly noisy and
  are preserved only as raw artifacts, not as the basis of the final
  recommendation.

## Recommendation

Keep only the smaller `datetime.datetime.fromisoformat()` entry fast
path:

- ASCII direct-buffer read
- conservative ASCII separator dispatch for `YYYY-MM-DD` and `YYYYMMDD`

Do not broaden it to `date.fromisoformat()` / `time.fromisoformat()`
without stronger evidence.

If we want substantially larger upside later, the next experiment should
be the more invasive one that originally motivated this item: a true
length-dispatched, digit-unrolled parser for the dominant datetime
layouts. The safe entry fast path tested here is worthwhile, but it is a
single-digit optimization, not the original 2–3x hypothesis.
